# lock-file-consumer

A test bed for **GitHub Actions lockfiles** (`.github/workflows/actions.lock`, generated by
[`gh actions-lock`](https://github.com/github/gh-actions-lock) v0.2.0, verified with v0.3.0).

Each scenario lives on its own branch with its own pull request, so you can see the behavior on GitHub directly.
Many scenarios reproduce the experiments in BoostSecurity's
[Pinning the unpinnable: GitHub Actions lockfiles](https://labs.boostsecurity.io/articles/pinning-the-unpinnable-github-actions-lockfiles/);
the others are new.

> **Two results per scenario.**
> - **GitHub result** is what GitHub's own lockfile enforcement does with the scenario's `ci.yml` run:
>   `startup_failure`, a failure in *Set up job*, or a locked, successful run.
> - **`--verify` result** comes from `verify-lockfile.yml` on the same branch. It's a copy of
>   [github/gh-actions-lock's workflow](https://github.com/github/gh-actions-lock/blob/main/.github/workflows/verify-lockfile.yml),
>   which runs `gh actions-lock --verify`, with the install pin bumped to **v0.3.0** (upstream's copy still pins v0.2.0).
>
> GitHub enforces the branch's lockfile on `verify-lockfile.yml` too. Its entry
> (`verify-lockfile.yml` → `actions/checkout@v7.0.1`) was **added to each branch's `actions.lock` by hand**,
> never with `gh actions-lock`, so the tampering under test is left as it was. Where the lockfile is
> missing or malformed, GitHub blocks `verify-lockfile.yml` as well (⛔).
>
> Legend for `--verify`: ✅ exit 0 · ❌ exit 1 (blocking findings) · 💥 exit 2 (the tool failed) ·
> ⛔ GitHub never started the workflow · 🆕 result or finding changed since v0.2.0. Each cell links to its run.
>
> The lockfiles were generated with v0.2.0 and are left as they are, so `--verify` judges exactly what was tested.
> The exceptions are labs 01 and 09: they test nothing in the lockfile, so they were relocked with v0.3.0 (`gh actions-lock --relock`).

## Key findings

1. **GitHub doesn't enforce "exact tag = exactly one commit"; only the CLI does.**
   - A lockfile that maps `v3.0.0` to an older commit in that tag's history runs the older code (lab 10).
   - A tag moved upstream is never reported by GitHub (lab 20).
   - Without a `--verify` job, a PR that changes only the lockfile can silently downgrade an action.
2. **Floating refs (`main`, `v4`) accept any commit in their history** (lab 11). Neither GitHub nor `--verify` notices a rollback. Read lockfile diffs carefully, or pin exact tags.
3. **GitHub is more lenient than the CLI in places.** With a `./` local action and a stale lockfile, the run still starts (lab 23), although the CLI refuses that workflow.
4. **Coverage is strict.**
   - Every workflow must be listed in the lockfile, including shell-only workflows, which need an empty `[]` entry (labs 04–07).
   - Every transitive dependency must be listed too (lab 17).
   - A malformed lockfile counts as a missing one (lab 03).
5. **Identity and history checks hold.** These are rejected:
   - a wrong `repo_id` (lab 15), though `owner_id` alone isn't checked (lab 16)
   - a commit outside the claimed ref (lab 13)
   - a deleted upstream branch (lab 19)
   - a fork-only imposter commit (labs 24–25; the article's bypass is fixed)
6. **Reusable workflows can't be locked by the caller.** The called workflow's tag must contain its own `actions.lock` (PR #2, lab 28).
7. **`$/` always resolves in the repository that defines it**, not in the caller's checked-out files (labs 21, 22, 29).
8. **Container images aren't locked.** Unpinned images still run. Since v0.3.0 the CLI warns about every unpinned image (`docker://` steps and job `container:`), but only as a warning (lab 26).
9. **GitHub fails in two different places.**
   - Coverage and parse problems stop the run before it starts (`startup_failure`, with an annotation on the run page that the REST API doesn't return).
   - Identity and ref checks fail later, in the job's *Set up job* step.

## `--verify` compared with GitHub

These results come from the `verify-lockfile.yml` runs of 2026-10-23 with gh-actions-lock **v0.3.0**, each linked in the tables above.

| | Labs | What happens |
|---|---|---|
| **`--verify` is stricter** | 10, 20, 23 | GitHub runs the workflow. `--verify` fails on an exact tag locked to a commit the tag no longer points at (10, 20, now named *Locked commit isn't the tag's commit*), and on the stale entry left by `--no-migrate-local-actions` (23; the `./` action itself is only a warning now). |
| **`--verify` rejects a v0.2.0 lockfile** | (01, 09 before relock), 10 | GitHub runs the workflow. v0.3.0 reports *Incomplete lockfile*: the v0.2.0 lock didn't record that `lock-file-action@v2.0.0` uses `actions/checkout@v7.0.1`. `gh actions-lock --relock` fixed labs 01 and 09 ([01](https://github.com/Exypte/lock-file-consumer/actions/runs/39921347696), [09](https://github.com/Exypte/lock-file-consumer/actions/runs/39921381406) before it), so they pass again. |
| **GitHub is stricter** | 28 | `--verify` passes, but GitHub stops a reusable workflow whose tag ships no lockfile. |
| **Both catch it** | 04, 05, 06, 08, 13, 15, 17, 19, 24, 25 | Missing coverage, ref changed without relocking, a commit outside its ref, a replaced repository, a missing transitive entry (17, 🆕 in v0.3.0), a deleted upstream branch, an imposter SHA in `uses:` (24) or in a hand-written lock (25, 🆕 in v0.3.0). |
| **Neither catches it** | 11, 16 | A floating branch locked to an older commit (11) and a tampered `owner_id` (16) pass both. |
| **Different failure** | 14 | GitHub reports *Invalid lockfile*. `--verify` still exits **2**, because the lockfile parser rejects it as unreadable ("action body ref … does not match pin key ref"). v0.3.0's fix for SHA refs covers only a SHA key whose `ref` is that same SHA, not a SHA `ref` under a tag key. |

Changes since v0.2.0 (runs of 2026-10-22): 17 and 25 went from ✅ to ❌, which closes two of the three gaps where GitHub was stricter. 01 and 09 went from ✅ to ❌ because of the lockfile format, and back to ✅ after `--relock`. 10, 20, 23 and 26 report different findings.

Takeaways:
- Running `--verify` in CI adds the exact-tag check (labs 10, 20), which is GitHub's main blind spot.
- `--verify` doesn't fully replace GitHub's enforcement: lab 28 passes `--verify` but is rejected at runtime.
- After upgrading to v0.3.0, run `gh actions-lock --relock` once. Lockfiles written by v0.2.0 can fail `--verify` even though GitHub accepts them (labs 01, 09).

## Dependency graph, dependency review and Dependabot alerts (PR #36)

The Go CLI from [Exypte/gh-actions-lock](https://github.com/Exypte/gh-actions-lock) (`main.go`, `cmd/`, `internal/`, `go.mod`, `go.sum`) was copied in so the dependency graph has Go modules to read next to the workflows. One Go dependency is vulnerable on purpose and used directly:

| Ecosystem | Dependency | Advisory | Fixed in |
|---|---|---|---|
| Go | `gopkg.in/yaml.v2 v2.2.7` (blank import in `main.go`, so `go mod tidy` keeps it) | [GHSA-wxc4-f4m6-wwqv](https://github.com/advisories/GHSA-wxc4-f4m6-wwqv) (medium) | v2.2.8 |

A vulnerable action (`actions/download-artifact@v4.1.2`, [GHSA-cxww-7g56-2vh6](https://github.com/advisories/GHSA-cxww-7g56-2vh6), high, fixed in v4.1.3) was tried in `ci.yml` here too, but dependency review never saw that file change, so it was removed. It is now tested on its own branch from `main` (`vulnerable-action`).

What was set up:

- `dependency-review.yml` runs `actions/dependency-review-action@v5.0.0` on pull requests with `fail-on-severity: low`.
- `dependabot.yml` gained a grouped `gomod` entry.
- Dependabot alerts and Dependabot security updates were turned on (both were off).
- The allowed-actions list gained `actions/download-artifact@*` and `actions/dependency-review-action@*`. `sha_pinning_required` is still on.
- `actions.lock` was relocked with `gh actions-lock` v0.4.0.
- Code scanning default setup (CodeQL, `go` and `actions`, weekly) was turned on after the merge.

The dependency graph and Dependabot alerts only read the default branch.

Results after the merge:

- Dependabot alert #1 opened for `gopkg.in/yaml.v2`, and security updates opened [#37](https://github.com/Exypte/lock-file-consumer/pull/37) (2.2.7 → 2.2.8).
- CodeQL default setup ran and passed (`go` and `actions` analyses, 0 alerts), even though `github/codeql-action` is **not** in the allowed-actions list and `sha_pinning_required` is on. The allow-list, SHA pinning and the require-lockfile policy don't apply to the dynamic default-setup workflow.

- `pull_request` vs `pull_request_target` lockfile selection
- A Docker action's own `runs.image`
- Tools an action downloads at runtime

## Reproduce

```sh
gh extension install github/gh-actions-lock --pin v0.3.0
gh actions-lock            # pin every workflow and write .github/workflows/actions.lock
gh actions-lock --verify   # read-only check (run in CI on every scenario PR by verify-lockfile.yml)
gh actions-lock --relock   # re-resolve every ref to its current upstream commit
```

To see why a run hit `startup_failure`, open the run page on github.com: the reason is shown as an annotation there.
